Getting Started
INTRODUCTION
Relay is a developer-first API gateway and management platform. It sits between your clients and your backend services, providing instant routing, rate limiting, authentication, and observability without complex configuration.
Why Relay?
Building APIs is easy, but operating them in production is hard. Relay handles the operational layer so you can focus on your actual service. Routing traffic through Relay gets you:
  • Automatic observability — every request is logged, timed, and analyzed without adding instrumentation to your own code.
  • Zero-config rate limiting — protect upstream services from abuse instantly, with rules you can change without a deploy.
  • API key management — issue, scope, and revoke keys without writing auth code.
How it works
When you create an API in Relay, you configure a target_url pointing at your backend. Relay assigns a public endpoint and transparently proxies traffic to that target while executing middleware — authentication, rate limiting, logging — at the edge, before your backend ever sees the request.
Every API belongs to exactly one environment (production, staging, or development), and every API key is scoped to exactly one environment. This keeps traffic, keys, and logs cleanly separated as you move from local testing to production.

Getting Started
QUICKSTART
Go from zero to a monitored, authenticated API in under five minutes.
1
Create an API
In the dashboard, click + New API and point it at your backend's base URL. This example proxies a public test API.
Copy# via the API — or use the dashboard "+ New API" button curl -X POST https://api.relay.dev/v1/apis \ -H "Authorization: Bearer $RELAY_TOKEN" \ -d '{"name":"Quickstart API","environment":"development","target_url":"https://jsonplaceholder.typicode.com"}'
2
Generate an API key
Keys authenticate requests made through Relay to your API — separate from the workspace token used to manage Relay itself.
Copycurl -X POST https://api.relay.dev/v1/keys \ -H "Authorization: Bearer $RELAY_TOKEN" \ -d '{"name":"Quickstart key","environment":"development"}'
3
Send your first request
Requests to your Relay-issued endpoint using the key from step 2 will now show up in Overview → Recent activity in real time.
Copycurl https://quickstart-api.relay.dev/posts/1 \ -H "Authorization: Bearer sk_dev_..."

AUTHENTICATION
There are two distinct authentication contexts in Relay — don't confuse them.
Managing Relay (workspace tokens)
Requests to the Relay management API (creating APIs, keys, webhooks, etc.) require a workspace-level access token in the Authorization header:
CopyAuthorization: Bearer relay_admin_<token>
Workspace tokens are generated in Settings → General and are scoped to the entire workspace, not a single environment. They cannot be used to authenticate proxied requests to your own APIs.
Calling your APIs through Relay (API keys)
Requests that go through Relay to your backend use an API key, scoped to a single environment, passed the same way:
CopyAuthorization: Bearer sk_live_<secret>
Error responses
A missing, malformed, or revoked token on either surface returns:
CopyHTTP/1.1 401 Unauthorized { "error": "unauthorized", "message": "Missing or invalid authentication token." }
Note — API keys and workspace tokens are not interchangeable. Using a workspace token to call a proxied API endpoint (or vice versa) returns the same 401 above.

ENVIRONMENTS
Every API and every key belongs to exactly one environment. Environments are isolated — they don't share traffic, keys, or logs.
ENVIRONMENTTYPICAL USENOTES
productionLive trafficCounted toward plan usage and billing.
stagingPre-release testingSame rate-limit defaults as production; separate key/log namespace.
developmentLocal/CI testingHigher default rate limits for iteration speed.
Switching environments
The environment switcher in the dashboard topbar changes which environment's data you're viewing — it does not move or copy resources between environments. To run the same API in two environments, create it twice with the same target_url and a different environment value.
API Keys
CREATE AN API KEY
POST/v1/keys
Creates a new API key scoped to a single environment. Keys are shown in full exactly once — store the returned secret immediately.
Note — the response's secret field is only ever returned on creation. Relay does not store or display full key values afterward.
Parameters
namerequired
string
A human-readable label, e.g. "CI pipeline".
environmentrequired
string
One of production, staging, development.
scopes
array
Permission scopes, e.g. ["read:requests","write:endpoints"]. Defaults to full access if omitted.
expires_at
string · ISO 8601
Optional expiration timestamp. Keys never expire by default.
Response
Returns the created key object, including the plaintext secret (shown once).
cURL
JavaScript
Python
Copy# create a production key curl -X POST https://api.relay.dev/v1/keys \ -H "Authorization: Bearer $RELAY_TOKEN" \ -H "Content-Type: application/json" \ -d '{ "name": "CI pipeline", "environment": "production" }'
Example response · 201 Created
{ "id": "key_8f2a1c", "name": "CI pipeline", "environment": "production", "secret": "sk_live_9f8e7d6c5b4a...", "created_at": "2026-09-11T10:42:00Z", "last_used_at": null }

API Keys
REVOKE AN API KEY
DELETE/v1/keys/:id
Immediately and permanently revokes a key. This cannot be undone.
Path parameters
idrequired
string
The key's ID, e.g. key_8f2a1c.
In-flight requests — requests already in progress when a key is revoked are not interrupted, but any new request authenticated with that key is rejected immediately with a 401.
Response
Returns 204 No Content on success. Revoking an already-revoked or nonexistent key returns a 404 (see Errors).
cURL
Copycurl -X DELETE https://api.relay.dev/v1/keys/key_8f2a1c \ -H "Authorization: Bearer $RELAY_TOKEN"
Response · 204 No Content

Webhooks
WEBHOOKS
Webhooks let Relay notify your systems in real time when something happens — a request fails, a key is created, an API's health status changes.
Delivery behavior
Each delivery is a POST with a JSON body and a Content-Type: application/json header. A delivery is considered successful on any 2xx response within 10 seconds.
Failed deliveries automatically retry with exponential backoff, up to 5 attempts over 3 hours, after which the delivery is marked permanently failed and visible in the dashboard's Webhooks page.
Getting started
  1. Go to Access → Webhooks in the dashboard and add an endpoint URL.
  2. Select which event types to subscribe to.
  3. Implement signature verification before trusting a payload.

Webhooks
VERIFYING SIGNATURES
Always verify a webhook's signature before trusting its payload — anyone can send a POST to your endpoint URL.
How it works
Every delivery includes a Relay-Signature header: an HMAC-SHA256 hash of the raw request body, signed with your webhook's signing secret (shown once when the webhook is created).
Verification example (Node.js)
Copyconst crypto = require('crypto'); function isValid(rawBody, signature, secret) { const expected = crypto .createHmac('sha256', secret) .update(rawBody) .digest('hex'); return crypto.timingSafeEqual( Buffer.from(expected), Buffer.from(signature) ); }
Important — compute the HMAC over the raw request body, before JSON parsing. Re-serializing the parsed object will produce a different signature and always fail verification.
